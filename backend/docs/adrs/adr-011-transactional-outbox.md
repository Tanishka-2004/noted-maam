# ADR-011: Transactional Outbox Pattern for Domain Events

**Status:** Accepted  
**Date:** 2026-07-10  
**Deciders:** Platform Engineering & Distributed Systems Architecture  

---

## Context

When a meeting lifecycle command completes, we must notify downstream AI and analytics pipelines by publishing integration events (e.g. `RecordingUploaded`, `MeetingEnded`). Publishing directly to the message bus (Redis Streams) during the HTTP request lifecycle introduces two failure modes:
1. **Dual-write failure**: If the database transaction succeeds but the message bus is offline, the event is lost.
2. **Ghost publication**: If the database transaction fails and rolls back but the event was already sent to the bus, downstream services process stale or non-existent meeting tasks.

---

## Decision

We will implement the **Transactional Outbox Pattern** to guarantee at-least-once event delivery:

1. **Transactional Insertion**: Domain events generated by the aggregate are mapped to outbox records and saved to an `outbox_events` database table inside the *same* database transaction as the domain entities.
2. **Outbox Schema**:
   The table will store complete event metadata, payload, and retry characteristics:
   - `id`: UUID (Primary Key)
   - `aggregate_id`: UUID
   - `aggregate_type`: String (e.g. `Meeting`)
   - `event_type`: String (e.g. `MeetingStarted`)
   - `event_version`: Integer (e.g. 1)
   - `payload`: JSONB (Serialized event attributes)
   - `status`: String (`PENDING`, `DELIVERED`, `FAILED`)
   - `retry_count`: Integer
   - `last_error`: String
   - `occurred_at`: Timestamp
   - `published_at`: Timestamp
3. **Dispatcher Abstraction**: The outbox dispatcher is decoupled behind an interface:
   ```python
   class EventDispatcher(ABC):
       @abstractmethod
       async def dispatch(self, event_id: uuid.UUID, event_type: str, payload: dict) -> None:
           """Publishes events to the specific message broker."""
           pass
   ```
   We will implement `RedisEventDispatcher` as the initial adapter.
4. **Polling Background Task**: A worker process queries the `outbox_events` table for `PENDING` records, publishes them to the message broker via the active dispatcher, and updates the status to `DELIVERED` transactionally.

---

## Domain vs Integration Events

To preserve security and service boundaries, we do not expose internal database/domain structures directly. The outbox dispatcher maps domain events to decoupled **Integration Events** carrying versioned schemas (e.g. `RecordingUploaded.v1`) before sending them to the Redis Stream.

---

## Consequences

- **Positive:** Guarantees at-least-once event delivery. Prevents ghost events on transaction rollbacks.
- **Positive:** Downstream message brokers can be swapped (e.g. Redis Streams to Kafka/RabbitMQ) by writing a new adapter class without changing domain code.
- **Negative:** Increased database storage and write load to capture outbox tables.
- **Complexity:** Requires background worker setup and handling of duplicate message delivery at the consumer level (idempotent consumers).
